12장

AI 도입 현실 점검

LLM을 NPC에 넣기 전에 비용, 응답 속도, 로컬 모델과 API, 일관성, 안전장치, 재현성을 따져야 한다. 대부분의 게임에서 현실적인 답은 "행동은 규칙, 말과 요약만 LLM"이다.

한눈에 보기#

질문 왜 중요한가
비용: NPC 한 명이 하루에 몇 번 모델을 부르나? 플레이어 수 × NPC 수 × 호출 수로 곱해진다
응답 속도: 몇 초 기다릴 수 있나? 대화는 1~2초, 하루 계획은 수십 초도 가능
로컬 vs API: 어디서 돌리나? 로컬은 사양과 품질, API는 비용·인터넷·서비스 종료 위험
일관성: 설정과 사실을 지키나? 설정 붕괴는 몰입을 깬다
안전장치: 이상한 출력을 막을 수 있나? 자유 입력은 공격 경로가 된다
재현성: 같은 상황에서 같은 결과가 나오나? 버그 재현, 세이브·로드, 밸런스 테스트

비용#

  • Generative Agents 논문의 저자들은 25명의 에이전트를 이틀 동안 시뮬레이션하는 데 토큰 비용으로 수천 달러가 들었고 실행에 여러 날이 걸렸다고 밝혔습니다(당시 gpt-3.5-turbo 기준). 공식 (Park 외 2023)
  • 모델 가격은 자주 바뀌므로 이 가이드에는 특정 가격을 적지 않았습니다. 대신 아래 식으로 직접 계산하세요.
하루 비용 ≈ 동시 플레이어 수 × 활성 NPC 수 × NPC당 하루 호출 수 × 호출당 평균 토큰 수 × 토큰당 가격

비용을 줄이는 방법:

  1. 호출 횟수를 줄인다: 하루 계획·회고는 하루 한 번, 대화는 플레이어가 말을 걸 때만. 화면 밖 NPC는 부르지 않습니다(AI LOD, 9장).
  2. 입력을 줄인다: 기억 전체가 아니라 검색으로 고른 몇 개만 넣습니다(5장).
  3. 결과를 저장해 재사용한다: 같은 상황의 대사·요약은 캐시합니다.
  4. 작은 모델을 쓴다: 표현만 맡기면 작은 모델로 충분한 경우가 많습니다. 추정

응답 속도#

  • 대화 대사처럼 플레이어가 기다리는 곳에는 시간 제한을 두고, 넘으면 미리 써 둔 대사를 쓰세요(7장).
  • 하루 계획·회고처럼 기다리지 않는 곳은 밤(잠자는 시간)이나 로딩 중에 미리 만들어 둡니다.
  • 커뮤니티 위키에 따르면 인조이는 5배속 이상에서 일기·속마음·일정 기능이 꺼집니다. 추정 (Fextralife) 시간을 빨리 돌리는 시뮬레이션에서 LLM 호출이 따라가지 못하는 문제를 보여 주는 예로 볼 수 있습니다. 추정

Unity에서 호출할 때

네트워크 호출이나 추론을 메인 스레드에서 기다리면 화면이 멈춥니다. async/await나 코루틴으로 비동기로 부르고, 결과가 올 때까지 NPC는 "생각하는 동작"(고개 갸웃, 말줄임표 말풍선)을 보여 주세요. 결과가 늦게 왔을 때 이미 상황이 바뀌었으면 버리는 처리도 필요합니다.

로컬 모델 vs API#

로컬(기기 안) API(서버)
비용 플레이어 기기가 부담, 서버 비용 없음 호출마다 비용
품질 작은 모델 위주 큰 모델 사용 가능
사양 GPU 메모리 필요 인터넷만 있으면 됨
응답 속도 기기 성능에 따름, 네트워크 지연 없음 네트워크 지연 + 서버 대기
장기 운영 게임과 함께 배포, 오프라인 가능 서비스 가격 변경·종료 위험
개인정보 기기 밖으로 안 나감 서버로 보냄
  • 실제 사례: 크래프톤은 인조이의 CPC(Co-Playable Character)를 NVIDIA ACE로 만든 기기 내 소형 언어 모델(on-device SLM) 기반이라고 발표했습니다. 공식 (크래프톤 보도자료) 모델 크기는 보도마다 달라 확인하지 못했습니다. 확인 못 함
  • 오픈소스 예: AI Town은 로컬 모델 실행기(Ollama)나 OpenAI 호환 API를 설정으로 바꿔 쓸 수 있게 되어 있습니다. 공식 (a16z-infra/ai-town)

일관성 유지#

  1. 원본은 데이터: 이름, 관계, 사실, 성격 수치는 게임 데이터가 원본이고, 프롬프트는 매번 그 데이터에서 만듭니다(4장 섞어 쓰기).
  2. 사실 묶음만 주기: "아래 사실만 사용하라"는 지시와 함께 필요한 사실만 넣고, 출력에 사실 묶음에 없는 고유명사·숫자·약속이 있으면 버립니다(7장).
  3. 출력을 믿지 않기: AI Town은 LLM이 매긴 중요도를 숫자로 읽지 못하면 5로 둡니다. 공식 (memory.ts) 모든 LLM 출력에 이런 기본값을 두세요.
  4. 결과를 판정하는 쪽을 따로 두기: Concordia는 "게임 마스터" 역할의 에이전트가 행동의 결과를 판정하는 구조를 씁니다. 공식 (Concordia) 게임에서는 판정 쪽을 LLM이 아니라 게임 규칙으로 두는 편이 안전합니다.

안전장치#

  • 자유 입력: 인조이처럼 플레이어가 자유 텍스트로 NPC에게 영향을 줄 수 있게 하면 공식 (NVIDIA), 플레이어가 "모든 규칙을 무시하라" 같은 입력으로 NPC를 조종하려 할 수 있습니다. 입력을 규칙(허용 행동 목록)으로 바꾼 뒤 모델에 넘기거나, 자유 입력은 표현에만 쓰고 게임 상태를 바꾸는 근거로 쓰지 마세요.
  • 출력 거르기: 금지어·개인정보·다른 작품의 고유명사 필터, 길이 제한, 형식 검사(JSON이면 파싱 실패 시 대체).
  • 연령 등급: 생성 결과가 게임의 등급을 넘지 않도록 프롬프트와 필터를 함께 씁니다.

재현성#

  • 전통 시스템은 무작위 시드를 고정하면 같은 상황에서 같은 결과가 나옵니다. 버그를 재현하고, 세이브를 불러와도 같은 일이 일어납니다.
  • LLM은 같은 입력에도 다른 출력이 나올 수 있습니다. 대책:
    1. 게임 상태를 바꾸는 결정은 LLM에게 맡기지 않는다. (가장 확실함)
    2. LLM 출력은 저장해 두고, 로드할 때 다시 생성하지 않고 저장된 문장을 씁니다.
    3. 프롬프트·모델 버전·출력을 로그로 남겨 문제가 생겼을 때 추적합니다.

AI 없이 / AI 사용 / 섞어 쓰기 비교표#

평가는 이 가이드에서 정리한 사례들을 바탕으로 한 상대 비교입니다. 프로젝트 규모와 모델 발전에 따라 달라집니다. 추정

기준 AI 없이 (전통) AI 사용 (LLM 중심) 섞어 쓰기
실행 비용 거의 없음 큼 (호출 수에 비례) 작음~중간 (표현·요약만)
표현 품질·다양성 쓴 만큼 매우 높음 높음
일관성 높음 (데이터가 원본) 낮음~중간 높음 (결정은 규칙)
개발 기간 콘텐츠 작성에 김 프로토타입은 빠름, 안정화가 김 시스템 + 프롬프트·검증 둘 다 필요
디버깅·재현성 쉬움 어려움 중간 (LLM 부분만 어려움)
위험 반복·단조로움 설정 붕괴, 부적절한 출력, 비용 폭증, 서비스 의존 LLM 부분 품질 편차
오프라인 가능 API면 불가 대체 대사로 가능
대표 사례 동숲, 스타듀, 림월드 Generative Agents, Project Sid 인조이(발표 기준 추정), 이 가이드의 구현 스케치

상황별 후보#

상황 권할 만한 후보들
1인·소규모, 출시가 목표 전통 + 대사 틀 / 전통 + 개발 중에만 LLM으로 대사 초안 생성 후 사람이 검수
대화가 핵심 재미 섞어 쓰기(규칙이 주제·사실 결정, LLM이 문장) / 소수 핵심 NPC만 LLM
연구·실험·잼 LLM 중심(Generative Agents·AI Town 구조)
대규모 NPC(수백 명) 전통 + AI LOD / 섞어 쓰기에서 LLM은 플레이어 근처 소수만

개발 도구로서의 LLM

게임 실행 중이 아니라 개발 중에 LLM을 쓰는 방법도 있습니다. 대사 후보·NPC 배경·사건 문구 초안을 생성하고 사람이 고쳐서 데이터에 넣으면, 실행 비용·일관성·재현성 문제가 모두 사라집니다. 대신 "매번 다른 대사"는 얻을 수 없습니다.
